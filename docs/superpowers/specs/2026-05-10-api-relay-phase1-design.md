# API 中转服务站第一阶段设计

日期：2026-05-10

## 1. 结论

第一阶段采用单机稳定方案：

```text
员工自由客户端
  -> Nginx
  -> New API
  -> Sub2API
  -> coding plan / API key 上游资源池
```

Metapi 暂不进入主链路；All API Hub 仅作为运维辅助参考，不作为生产服务端组件。

核心原则：

- New API 负责员工用户、个人 Token、余额、免费额度、模型权限、计费和审计。
- Sub2API 负责上游订阅号/API key 调度、粘性会话、并发槽位、限流冷却和账号恢复。
- 支付不是第一阶段核心链路；余额/额度才是核心链路。充值来源可先由管理员手工处理。
- 员工可看到并使用真实模型名，但仍通过白名单、价格、余额和风控限制控制成本。
- 默认不记录 prompt/completion 原文，只记录用量和排障元数据。

## 2. 当前约束

- 初始员工数量约 10 人。
- 并发和请求量未知，需要通过灰度运行观测。
- 主要使用场景是 coding plan / coding agent / OpenAI-compatible 类客户端。
- 客户端会混合使用，不强制统一。
- 第一阶段先单机稳定，不做多副本高可用。
- 合作付费模式：员工有一定免费额度，超出后可自付费继续使用。

## 3. 组件职责

### 3.1 Nginx

职责：

- TLS 终止。
- 管理端访问限制。
- 请求体限制。
- Header 规范化。
- 禁止或弱化 query API key 日志泄露。
- 保证下划线 Header 可用。

关键要求：

```nginx
underscores_in_headers on;
```

原因：Sub2API 的粘性会话可读取 `session_id` / `conversation_id`，如果反代丢弃下划线 Header，coding 类长会话稳定性会下降。

### 3.2 New API

职责：

- 每个员工一个 New API 用户账号。
- 每个员工至少一个个人 API Token。
- 员工余额、免费额度、用量扣费。
- 真实模型名展示与模型白名单。
- 员工侧 usage log 与成本统计。
- 对接 Sub2API 作为 OpenAI-compatible / Claude / Gemini 等上游渠道。
- 控制全局重试次数，避免重试风暴。

### 3.3 Sub2API

职责：

- 管理多个上游订阅号/API key/coding plan 资源。
- 对上游账号做模型能力、并发、优先级和负载调度。
- 支持粘性会话。
- 处理 401/403/429/529 等上游错误，做冷却、临时不可调度或恢复。
- 通过 Redis 管理并发槽位和等待队列。

### 3.4 Postgres 与 Redis

即使第一阶段是单机，也建议使用 Postgres 和 Redis：

- Postgres 保存用户、Token、余额、渠道、计费、日志等状态。
- Redis 支撑缓存、限流、并发槽位、等待队列等运行态。
- 后续扩展到多副本时迁移成本低。

## 4. 员工与 Token 设计

### 4.1 用户主体

每名员工创建一个 New API 用户账号。用户账号是以下能力的主体：

- 免费额度。
- 自费余额。
- 多个 API Token。
- 用量统计。
- 异常停用。
- 后续支付/充值扩展。

不建议只发裸 Token，因为裸 Token 模式不利于后续余额、自助查询和责任追踪。

### 4.2 Token 命名

如果员工使用多个客户端，可给多个 Token，但都归属同一用户。

命名建议：

```text
alice-main
alice-cursor
alice-cli
bob-main
```

### 4.3 Token 策略

每个 Token 至少配置：

- 启用状态。
- 所属用户。
- 所属分组。
- 过期时间。
- 可用模型白名单。
- 可选 IP 白名单。
- 剩余额度或依赖用户余额。

泄露或异常时，可以停用单个 Token，不必停用整个用户。

## 5. 余额、免费额度与付费

### 5.1 第一阶段充值模型

第一阶段不接在线支付。采用：

```text
员工付款 / 内部登记 / 免费发放
  -> 管理员手工调整 New API 用户余额或订阅额度
```

这不影响 API 请求主链路。

### 5.2 费用主账本

员工侧准账以 New API 为准：

```text
员工费用：New API usage / billing
上游资源状态：Sub2API account / key usage
人工核对：管理员按需对齐两边差异
```

Sub2API 不作为员工侧扣费准账，它用于上游资源池调度和成本辅助分析。

### 5.3 免费额度

建议每月给员工发放固定免费额度：

```text
基础免费额度：按公司预算确定
超出后：员工自费或管理员追加余额
```

高价模型可以不纳入免费额度，或给更低免费上限。

### 5.4 防浪费控制

第一阶段至少需要：

- 用户余额不足即拒绝请求。
- 每人月免费额度有限。
- 每人日消耗告警。
- 高价模型单独白名单。
- 单请求最大预扣费。
- 单用户/Token 可停用。
- usage log 可按用户、Token、模型、时间、费用查询。

## 6. 模型策略

用户要求展示真实模型名，因此第一阶段不使用 `company-code-fast` 这类公司别名。

模型开放方式：

- 使用真实模型名。
- 仍通过 New API 模型白名单控制可用范围。
- 按成本和稳定性分层开放。

建议分层：

```text
基础模型：
  - 日常 coding/chat
  - 可用免费额度

高价模型：
  - 高质量 coding / 长上下文
  - 需要余额充足
  - 可设置更低日限额

实验模型：
  - 新模型或不稳定模型
  - 小额度
  - 可随时下架
```

真实模型名不等于所有模型无差别开放。

## 7. 混合客户端支持策略

员工可自由使用客户端，但平台只对第一阶段明确列出的 L1 客户端提供配置模板和稳定性保障。

### 7.1 L1：正式支持

- OpenAI SDK / OpenAI-compatible 客户端。
- Cursor / Cline / Continue 等可配置 OpenAI-compatible base URL 的客户端。
- Codex CLI / coding agent 类客户端。
- Claude Code 类客户端，视其协议支持情况走 Claude `/v1/messages` 或 OpenAI-compatible 方式。

### 7.2 L2：尽力支持

员工自选的第三方客户端，只要支持标准 OpenAI-compatible API，可尝试使用。出现问题时，先要求用 L1 模板复现。

### 7.3 L3：第一阶段不承诺

- 使用 query key 的客户端。
- 非标准代理协议。
- 大规模文件/图片/视频任务。
- 会把 API key 同步到不可信云端的插件。
- 无法配置 base URL 或无法关闭异常重试的客户端。

## 8. 粘性会话设计

coding 类场景通常存在长会话和上下文缓存需求。第一阶段需要尽量保持会话粘性。

### 8.1 Header 透传

New API 对接 Sub2API 的渠道建议配置 Header Override：

```json
{
  "session_id": "{client_header:session_id}",
  "conversation_id": "{client_header:conversation_id}"
}
```

### 8.2 Body 字段

Sub2API 可读取 `prompt_cache_key` 作为 session hash 来源。支持该字段的客户端应优先保留。

### 8.3 Fallback

如果客户端不提供 `session_id`、`conversation_id`、`prompt_cache_key`，Sub2API 会根据模型、system、tools 和首条 user 消息生成 fallback hash。该模式可用，但稳定性弱于显式 session。

## 9. 重试与故障控制

混合客户端可能自带重试，因此服务端重试必须保守。

建议：

- New API `RetryTimes = 1`，最多不超过 2。
- Sub2API 负责账号池调度、等待队列、限流冷却和临时不可调度。
- 不做无限等待。
- 401/403/429/529 等上游错误主要由 Sub2API 做账号状态处理。
- 对粘性强的 coding 会话，避免跨多个互不共享状态的池激进切换。

故障目标：

- 单个上游账号异常不影响整个员工入口。
- 单个员工异常使用不影响其他员工。
- 短时上游限流不导致全局雪崩。

## 10. 日志与隐私

第一阶段默认不记录：

- prompt 原文。
- completion 原文。
- 上传文件内容。
- 工具调用参数原文。
- API key / Authorization 原文。

保留排障和计费元数据：

- request_id。
- 用户 ID / 用户名。
- Token ID / Token 名称。
- 模型名。
- 状态码。
- 错误码。
- 是否流式。
- input/output tokens。
- 费用。
- 延迟。
- TTFT。
- 使用渠道。
- 重试链路。
- 创建时间。

后续如需记录 prompt/completion，应作为单独升级方案，并需要明确保留周期、脱敏规则、访问权限和员工告知。

## 11. 安全基线

必须项：

- 管理后台只允许内网/VPN/IP 白名单访问。
- New API、Sub2API、数据库、Redis 不暴露到公网。
- 禁止默认弱密码和默认 token。
- New API 设置强 `SESSION_SECRET`。
- Sub2API 生产环境启用 URL allowlist，禁止私网目标和非 HTTPS 上游。
- CORS 只允许可信域名。
- 反代层限制请求体大小。
- 禁止 query API key 或至少不记录 query。
- 员工 Token 泄露时可在 5 分钟内停用。

## 12. 单机部署建议

第一阶段单机组件：

```text
Nginx
New API
Sub2API
Postgres
Redis
基础日志/监控
```

部署原则：

- 镜像版本固定，不使用 `latest`。
- 数据目录持久化。
- Postgres 定时备份。
- Redis 持久化按需求开启。
- 配置文件纳入备份。
- 升级先在测试环境验证。

## 13. 观测指标

第一阶段至少看 7 天数据再扩容或改架构。

关键指标：

- 每日请求数。
- 峰值并发。
- 每员工成本。
- 每模型成本。
- 错误率。
- 429/401/403/529 次数。
- P95/P99 延迟。
- TTFT。
- 流式中断率。
- New API 重试次数。
- Sub2API 排队时间。
- 账号冷却数量。
- 余额不足次数。

## 14. 员工使用规则

必须告知员工：

- 每人只能使用自己的 API key。
- 不允许共享 key。
- 不允许把 key 填入不可信网页或会云同步的插件。
- 自由客户端可用，但官方只保障 L1 客户端模板。
- 非 L1 客户端出问题，先用官方模板复现。
- 高消耗任务或自动化批量任务需要提前说明。
- 超出免费额度后需要自费或申请追加额度。

## 15. 第一阶段验收标准

达到以下条件才算第一阶段稳定：

- 连续 7 天无需人工重启。
- 每个员工独立用户、独立 Token、独立余额。
- 员工能看到真实模型名。
- 免费额度和自费余额扣减流程正常。
- 不记录 prompt/completion 原文。
- usage 元数据足够定位成本和错误。
- 单个 Token 可快速停用。
- 单个上游账号异常不会导致全站不可用。
- Redis/Postgres 重启后服务可恢复。
- 能回答：谁用了多少、哪个模型最贵、哪个账号池最不稳。

## 16. 后续升级项

可后置：

- 在线支付。
- 企业 SSO。
- 多机高可用。
- Metapi 二级聚合。
- 自动余额预警和自助充值。
- Prompt/completion 采样日志。
- 财务对账系统。
- 公司模型别名。

触发条件：

- 员工数量明显增加。
- 单机资源不足。
- 多个 Sub2API 池需要统一调度。
- 需要跨区域容灾。
- 员工自助充值需求明确。
- 审计/合规要求提升。

## 17. 仍需确认

进入实施前还需要确定：

1. 第一批真实模型名单。
2. 每人每月免费额度。
3. 高价模型是否允许使用免费额度。
4. 充值/加余额的人工流程。
5. 第一批 L1 客户端清单和配置模板。
6. 单机部署所在服务器规格。
7. 管理后台允许访问的 IP/VPN 范围。
